# 平台系统集成测试方案

## 1. 文档目标

本文档用于定义 CloudCTF 平台的系统集成测试范围、执行流程、验收标准与后续 CI/CD 自动化接入方向。

目标是保证在代码提交到 CI/CD 后，可以自动启动完整平台，并验证以下关键链路：

1. 管理端基础配置与比赛编排流程可用。
2. 内置资源同步链路可用。
3. 模板编译链路可用。
4. 题目与资源绑定链路可用。
5. 比赛开始前访问控制正确。
6. 比赛开始后答题与交卷链路可用。
7. 漏洞复现环境启动链路可用。

## 2. 测试范围

本次系统测试覆盖以下模块：

1. 管理后台认证与业务编排。
2. 用户、队伍、比赛、题目、理论试卷管理。
3. 资源仓库同步。
4. 模板编译与模板状态更新。
5. CTF 练习场与比赛题目绑定。
6. 比赛时间控制与权限控制。
7. Flag 提交、理论答题与试卷提交。
8. 漏洞环境启动与容器运行状态检查。

本次测试暂不覆盖：

1. 历史数据迁移校验。
2. 大规模性能压测。
3. 多节点高可用部署。
4. 邮件、短信、第三方告警集成。

## 3. 测试环境要求

建议在 CI 集成环境中准备一套独立测试环境，要求如下：

1. 可启动前端、后端、数据库。
2. 可访问 Docker 或等价容器运行时。
3. 支持模板编译、容器拉起、容器状态查询。
4. 测试环境网络允许访问内置资源仓库或内置同步源。
5. 每次测试使用独立数据库或临时数据库，避免测试互相污染。

建议环境变量至少包括：

1. 管理员初始账号信息。
2. 数据库连接信息。
3. Docker / 虚拟化主机连接信息。
4. 测试用资源仓库配置。
5. 平台基础访问地址。

## 4. 测试数据设计

建议固定使用以下测试对象，保证脚本可重复执行：

1. 管理员账号：`admin`
2. 队伍：`ci-team-01`
3. 普通用户：`ci-player-01`
4. CTF 比赛：`CI CTF Competition`
5. 理论赛比赛：`CI Theory Competition`
6. CTF 题目模板资源：`F12`
7. 漏洞模板资源：`tomcat`
8. 理论试卷：`CI Theory Paper`

建议所有测试对象命名加 `ci-` 前缀，便于隔离与清理。

## 5. 测试前置条件

执行前需要确认：

1. 平台服务已正常启动。
2. 数据库已完成 schema 初始化。
3. 管理员账号可登录。
4. 默认虚拟化主机配置可用。
5. 内置资源源中存在 CTFDB 与 vulhub 可同步内容。
6. F12 与 tomcat 资源可被成功同步并参与编译。

## 6. 核心测试流程

### 6.1 管理端基础编排

#### 目标

验证管理员可以完成完整的比赛与用户初始化流程。

#### 步骤

1. 登录管理系统。
2. 创建测试队伍 `ci-team-01`。
3. 创建测试用户 `ci-player-01`。
4. 将测试用户加入测试队伍。
5. 创建一个 CTF 比赛 `CI CTF Competition`。
6. 创建一个理论赛比赛 `CI Theory Competition`。
7. 为 CTF 比赛添加至少一道比赛题目。
8. 为理论赛比赛创建并绑定一套试卷，或绑定已有理论题。

#### 验收标准

1. 所有创建接口返回成功。
2. 队伍、用户、比赛、题目、试卷均可在管理端列表查询到。
3. 比赛与题目、比赛与试卷的绑定关系正确。

### 6.2 同步内置资源

#### 目标

验证 CTFDB 与 vulhub 内置资源同步能力正常。

#### 步骤

1. 在管理端触发 CTFDB 资源同步。
2. 检查同步任务状态与同步日志。
3. 确认至少同步出目标资源 `F12`。
4. 在管理端触发 vulhub 资源同步。
5. 检查同步任务状态与同步日志。
6. 确认至少同步出目标资源 `tomcat`。

#### 验收标准

1. 同步接口返回成功。
2. 同步日志状态为成功、完成或等价成功状态。
3. 模板列表中可以查询到 `F12` 与 `tomcat`。
4. 模板状态、路径、来源仓库等关键字段完整。

### 6.3 编译 F12 与 tomcat 资源

#### 目标

验证模板编译链路正常。

#### 步骤

1. 对 `F12` 模板触发编译。
2. 轮询构建任务状态与构建日志。
3. 验证 `F12` 模板最终状态为 `completed`、`ready` 或平台定义的成功状态。
4. 对 `tomcat` 模板触发编译。
5. 轮询构建任务状态与构建日志。
6. 验证 `tomcat` 模板最终状态为 `completed`、`ready` 或平台定义的成功状态。

#### 验收标准

1. 两个模板均能进入构建流程。
2. 构建日志中无致命错误。
3. 模板最终状态为成功。
4. 模板端口、服务信息等运行时元数据被正确生成。

### 6.4 将 F12 资源添加到练习场和比赛题目

#### 目标

验证模板与题目绑定逻辑可用。

#### 步骤

1. 在练习场创建一个使用 `F12` 模板的动态题目。
2. 在 CTF 比赛中创建或更新一道比赛题目，并绑定 `F12` 模板。
3. 确认题目启用了动态容器或关联模板字段。
4. 使用管理端查看题目详情，确认模板绑定关系。

#### 验收标准

1. 练习场动态题目创建成功。
2. 比赛题目绑定模板成功。
3. 题目详情中能看到正确的模板 ID、主机 ID、动态标记等字段。

### 6.5 比赛未开始前的访问控制测试

#### 目标

验证比赛开始前用户不能越权获取或提交比赛内容。

#### 步骤

1. 使用测试用户登录前台。
2. 访问 CTF 比赛详情页或题目列表。
3. 尝试获取比赛题目详情。
4. 尝试提交 Flag。
5. 访问理论赛比赛详情页或试卷页面。
6. 尝试获取试卷内容。
7. 尝试提交理论试卷。

#### 验收标准

1. 未开始比赛的题目访问应被拒绝，或返回空列表，或返回未开始状态。
2. 未开始比赛的 Flag 提交应失败。
3. 未开始比赛的试卷获取应失败，或返回未开始状态。
4. 未开始比赛的试卷提交应失败。

### 6.6 开始比赛

#### 目标

验证比赛状态流转正常。

#### 步骤

1. 将 CTF 比赛状态切换为开始，或将比赛时间设置到当前时刻。
2. 将理论赛比赛状态切换为开始，或将比赛时间设置到当前时刻。
3. 重新获取比赛详情。
4. 确认前台用户可见比赛状态已更新。

#### 验收标准

1. 比赛状态更新成功。
2. 前后台查询结果一致。
3. 平台将比赛识别为进行中状态。

### 6.7 比赛开始后的答题与交卷测试

#### 目标

验证比赛开始后核心业务链路正常。

#### 步骤

1. 使用测试用户访问 CTF 比赛题目列表。
2. 获取比赛题目详情。
3. 提交一次错误 Flag，验证失败路径。
4. 提交一次正确 Flag，验证成功路径。
5. 验证积分、解题状态、提交记录更新。
6. 使用测试用户访问理论赛试卷。
7. 提交理论试卷答案。
8. 验证试卷提交记录、得分、状态更新。

#### 验收标准

1. 比赛开始后题目可正常获取。
2. 错误 Flag 返回失败。
3. 正确 Flag 返回成功。
4. 提交记录、解题状态、排行榜或积分状态正确更新。
5. 理论试卷可正常获取。
6. 理论试卷可正常提交。
7. 提交后系统生成提交记录与评分结果，或进入待评分状态。

### 6.8 漏洞复现环境启动测试

#### 目标

验证漏洞环境可以基于模板成功启动。

#### 步骤

1. 选择基于 `tomcat` 模板的漏洞环境或动态容器资源。
2. 触发环境启动。
3. 轮询容器组状态。
4. 校验容器组状态从 `creating` 进入 `running`。
5. 获取容器端口映射、访问地址、容器 ID 等运行信息。
6. 对暴露端口执行一次基础连通性检查。

#### 验收标准

1. 启动接口返回成功。
2. 容器组成功创建。
3. 容器最终状态为运行中。
4. 运行时访问地址和端口信息完整。
5. 至少一个业务端口可连接。

## 7. 结果判定

本轮系统集成测试通过的最低标准如下：

1. 8 个测试阶段全部执行完成。
2. 不允许出现平台启动失败、资源同步失败、模板编译失败、比赛状态错误、环境启动失败。
3. 比赛未开始前必须阻止答题和交卷。
4. 比赛开始后必须允许答题和交卷。
5. F12 与 tomcat 两个目标资源必须完成同步和编译。

若任意关键步骤失败，应视为本轮集成测试失败。

## 8. 建议的自动化拆分

建议后续将自动化拆成以下测试套件：

1. `suite_admin_setup`
2. `suite_resource_sync`
3. `suite_template_build`
4. `suite_competition_access_control`
5. `suite_competition_submission`
6. `suite_runtime_environment`

这样可以在 CI 中实现：

1. 失败快速定位。
2. 支持并行执行。
3. 支持只重跑失败套件。

## 9. CI/CD 接入建议

后续接入 CI/CD 时建议采用以下流程：

1. 启动数据库与平台服务。
2. 等待健康检查通过。
3. 注入测试管理员账号与测试环境配置。
4. 执行系统集成测试脚本。
5. 收集测试日志、接口响应、构建日志、容器日志。
6. 失败时上传产物供排查。
7. 成功后销毁测试环境。

建议至少保存以下测试产物：

1. 平台后端日志。
2. 资源同步日志。
3. 模板编译日志。
4. 测试请求响应日志。
5. 容器组状态快照。
